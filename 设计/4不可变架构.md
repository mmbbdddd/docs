# 不可变架构

随着docker，广为人只知。

docker解决了软件对环境的依赖产生的不可靠，不健壮的问题。

给出了轻量级的虚拟化方案，在这种不可变的基础上，从而有了更上层的编排，管理，弹性……等等

否则一切建于流沙之上。

类似的还有JS。

JS在JS5模块化规范成熟以前，发展了10多年，只是浏览器中的一个小脚本，甚至众多技术如RCP、flash、WFP、……等虎视眈眈
在JS5模块化规范之后，前端技术几年时间就迅速百花齐放……它甚至开始入侵Java在服务器端的开发地位，甚至产生了WASM
这样的底层技术，有了挑战系统编程的资格。

这也是模块化带来的不可变契约产生的涌现。

然而，世界的本质是变化的。不可变技术的关键，是通过什么杨的设计，如何化变化为不变。

# 不可变架构最佳实践

|        | 职责      | 最佳实践                         | 
|--------|---------|------------------------------| 
| Docker | 屏蔽基础设施的变化 | Docker                       | 
| 脚手架    | 屏蔽技术组件的变化 | springcloud                  | 
| 网关     | 屏蔽服务协议变化 | apisix，业务网关                  | 
| ETL    | 屏蔽数据源的变化 | spark                        |  
| api    | 屏蔽实现变化  |                              | 
| el     | 屏蔽数据格式变化 | mvel，ognl                    | 
| 配置文件   | 屏蔽环境变化  |                              | 
| 配置表    | 屏蔽业务参数变化 |                              | 
| 流程编排   | 屏蔽流程变化  | pipeline,pc,liteflow         | 
| PaaS   | 某一类通用技术能力 | redis、监控平台                   | 
| APaaS  | 某一类通用业务能力 | 渠道网关、费率平台                    |  
| 引擎     | 多种变化的关系 | 浏览器（样式/内容/行为）、风控引擎（数据/逻辑/流程） |
