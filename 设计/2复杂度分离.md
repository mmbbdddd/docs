# 什么是复杂度分离

复杂度分离是架构设计中的一个重要原则。它的核心思想是将系统中的不同复杂度的部分进行分离， 降低复杂度彼此耦合产生的超高复杂度。
提高系统的可维护性、可扩展性和可靠性。

举个例子：
假设我们开发一个贷款系统。
    
    1，上游是各式各样的客户、产品模式。
        这里的业务要求是尽量快多的产品，尽量快的迭代。
    2，下游是各式各样的资金渠道、不同资金渠道、资金产品有不同的费率、精度、取整方式等。
        这里的要求是金额计算一定不能错。
    3，在业务代码中，订单过来，路由到渠道，进行费率计算。以及按产品流程走。代码是彼此交织在一起的。
        如果产品需求快速迭代，影响到了费率计算逻辑，必然会引入bug。
        如果费率计算逻辑慎而又慎，必然影响产品快速迭代。

这2个要求是不可能同时实现的。 架构设计中，针对这种情况的解决方案是复杂度分离。例如

    1，公式引擎：可配置各种公式算法、精度、取整配置方式等、**实现高精度、高一致性金额计算的要求**。
    2，业务中台：流程编排 + 业务组件引擎 + 业务配置 实现各种业务的积木化组装配置。**实现业务快速迭代**
    3，底层基础设施、脚手架:实现高可用、高可靠

在没有分离的情况下，他们的复杂度是彼此叠加的。可靠性、可维护性是指数级降低的。他们都是一个个比较简单的问题。

# 识别复杂度：三离四化

复杂度分离的第一步是识别系统中的复杂度。

但是上面例子中的公式引擎的设计，其实在设计早期很难提炼出来————我看到很多信贷企业都是后期重构以后追加的。

但其实遵循一定的设计方法可以提前识别出来。

**有一个口诀：三离四化**

**三离**

1，业务和技术分离 （技术透明）

2，技术和部署分离 （规模透明）

3，变化和不变分离  (业务变化透明)

**四化**

1，变化的配置  **参数化**

2，变化的逻辑   **脚本化**

3，变化的业务流程  **流程编排化**

4，变化的解析、执行  **引擎化**


按如上的方法，在做领域事件风暴的时候，就有一定概率识别出接入渠道费率公式、计算精度、取整方式不同。理应有相应的配置表和引擎组件。


# 复杂度的耦合和分离
既有分，必有合。

微服务应用分了，则必有聚合应用，或者ESB、或网关做服务聚合。

分库分表既然数据分了，则必有ETL，或者大数据做数据聚合。

MVC中M和C分了，需M表达彼此的耦合关系。

费率平台将产品和渠道的费率计算分了。则必然在还款计划中、或者清算系统中，对彼此的整体费用计算关系做一个表达。

组件化、积木化的架构分了，则必然通过事务脚本（servlet，applet，servless）或者流程编排做业务聚合。

……

复杂度分离，核心的设计要点是

1，明白为什么要分，分的好处和收益是什么

2，分之后在哪里合，分合之上的整体模型是什么

|      | 收益/场景        | 缺点                                                       | 解决方案                    |
|------|--------------|----------------------------------------------------------|-------------------------|
| MVC  | 客户体验提升、专业化分工 | 后端耦合                                                     | M,API接口                 |
| 分层   | 复用性、可靠性      | 需抽象通用能力接口                                                | +防腐层                    |
| 微服务  | 领域划分         | 1需划分领域 <br/>2划分不当数据完整性和业务连续性、一致性降低<br/>3IO，提升错误率提升，需重试组件 | 更丰富的组件，更丰富的最佳实践经验       |
| 分库分表 | 性能提升         | 1限制跨表/库SQL                                               | CQRS                    |
| 组件化  | 复用性提升        | 不能耦合entity。否则耦合性提升                                       | 代码级复用意义不大，架构级、模块级复用有意义。 | 
| 费率平台 | 一致性和可变性分离    | 一致性的完整性不完整                                               | 在清算或者订单层需给出完整费率分配视图。    |
