# 什么是关注点分离
    
关注点分离是一种软件设计原则，旨在将不同复杂度分离到具有不同专业能力的人，以实现更高专业程度的工程协作，制作出更高质量的软件。

复杂度解决能力即专业能力的体现，也就是关注点。

最著名的关注点分离是MVC模式。

    V：前端、用户体验、产品经理。
    C：后端，复杂的业务逻辑、数据处理。
    M：前后端通过数据模型隔离，交互。

另外一个大家没有注意到但也比较知名的是JEE架构模式，不过它的设计比较生硬。

| 角色    | 职责            | 提交物                  | 描述          |
|-------|---------------|----------------------|-------------| 
| 开发    | 开发业务逻辑        | EJB、Servlet、Applet扩展 | 企业的业务开发     | 
| 组件    | 开发通用组件        | *-api                | JEE厂商提供通用组件 | 
| 容器    | 开发通用组件        | tomcat、WebSphere    | JEE厂商提供容器   | 
| 组装者   | 组装逻辑、组件为部署描述符 | ejb.xml,web.xml      | 企业的业务开发     | 
| 部署者   | 部署、容器运维       | ear,war              | 企业的运维       | 
| Admin | 系统监控、运维       |                      | 企业的运维       | 


当前软件研发行业比较痛点的问题是：

    1. 90%的软件质量都堪忧，核心问题是懂业务的不懂技术，不懂设计；懂技术的不懂业务，无法设计。
    2. 大多数公司都会设计一些协作机制，让他们尽可能实现能力融合。
      比如要求技术人员学业务，进行大量业务培训。不过几乎看不到软件质量有什么改进。
      比如某些公司有产品、架构、PM三驾马车，不过软件还是迟迟难产。

如何对业务、技术进行关注点分离是当前大多数软件公司非常关注的问题。
 

# 企业的探索（Halo/Cola、ExpressQL）和思考

阿里中台有三大项目：业务中台，技术中台，数据中台。

后两者可以认为是成功的，前者失败——但恰好中台运动是他的战略目标。所以整体上，中台算是失败了。因为中台的失败，2019年以前在各个业务上高歌猛进的阿里，被迫放弃“阿里全向图愿景”，收缩业务，提出“阿里只做被集成”。

但阿里在中台架构上的技术探索，是很有价值的，其核心组件就是以流程编排和表达式引擎为中心的技术组件。
一个解决流程的变化、一个解决数据和逻辑的变化。
流程引擎是Halo和Cola这两个框架的核心。
而表达式引擎ExpressQL是阿里在中台运动以前就探索出来的，解决业务碎片化扩展和变化的关键技术组件。

理念上非常完美。

但实际上，阿里中台运动的失败，更多是业务和组织问题。

1. 一方面，中台化的组织团队，成为效率单点。中台团队凭借好恶和利益来响应其他业务团队。
2. 另外一方面，业务其实没有什么增量市场——中台团队就必然很难从原有研发团队系统中成功重构。 这也是马云说的问题——不能下雨天修房子，陷入困境后做技术改造，复杂度是叠加的，无解的。
3. 第三，从实践看，即使原有团队原地做重构，成功的概率也不高；比如阿里、恒生、赢时胜……其新一代微服务/中台系统都不成功。

**这证明了当前新一代软件危机的根源既不是技术复杂度、也不是业务复杂度、也不是他们的融合。**

    阿里有足够的技术、恒生有足够的业务、阿里中台项目很多团队都是原地重构，既懂业务也懂技术。

**而是如何能找出一个方法，不要让复杂度融合在一起，或压在一个人身上；要将复杂度分离、孤立成干脆的简单的复杂度，让特定的人能做到极致。**

    如
    
    1. 定义业务领域语言DSL，业务人员只需要关注特定的DSL，就能配置出无穷的业务变化
    2. 而技术人员只需要关注如何解析执行DSL
    
    思想和MVC差不多。

问题的关键是：

没有从管理上提出明确的要求，或者个别人虽有想法，但缺乏工程化的系统协同与探索落地。
