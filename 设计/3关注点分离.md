# 关注点分离
# 什么是关注点分离
    
关注点分离是一种软件设计原则，旨在将不同复杂度分离到具有不同专业能力的人。实现更高专业程度的工程协作，制作出更高质量的软件。

最出名的关注点分离是MVC模式。

    V:  = 前端、用户体验、产品经理。
    C:  = 后端，复杂的业务逻辑、数据处理。
    M:  = 前后端通过数据模型隔离，交互。

另外一个大家没有注意到但也比较知名的是JEE架构模式

| 角色    | 职责            | 提交物                  | 描述          |
|-------|---------------|----------------------|-------------| 
| 开发    | 开发业务逻辑        | EJB、Servlet、Applet扩展 | 企业的业务开发     | 
| 组件    | 开发通用组件        | *-api                | JEE厂商提供通用组件 | 
| 容器    | 开发通用组件        | tomcat,webshere      | JEE厂商提供容器   | 
| 组装者   | 组装逻辑、组件为部署描述符 | ejb.xml,web.xml      | 企业的业务开发     | 
| 部署者   | 部署、容器运维       | ear,war              | 企业的运维       | 
| Admin | 系统监控、运维       |                      | 企业的运维       | 

# 关注点分离的目的

和复杂度分离是架构上被动的应对，分离复杂度不同。

关注点分离是根据业务、或者产品的需求主动引入不同的专业人员（复杂度）、给专业人员设计合适的提交物、
实现专业人员无需懂开发、开发无需懂业务的高效协作方式，但软件能力1+1>2的复杂软件。

关注点分离的核心关切的不是复杂度，而是专业度。

分离出的组件往往是聚焦执行、解析领域语言(DSL)，让专业人员能专注于自己的专业领域，
 

# DSL

架构师的一个核心职责，就是为不同的专业人员确定合适的DSL.如果没有，就创造它。

    例如
    前端的DSL是HTML、CSS、JS. 
    数据分析的DSL是SQL. 
    后端的DSL是Java、C#、Python等。 
    风控业务的DSL是规则、决策树……等。 
    产品需求的DSL是ER模型和配置。

举个例子

    国内某知名集团很早的时候就看好AI+医疗。在OpenAI火之前就花费80亿美刀从IBM手中收购了做医疗AI的Watson Health。
    但是他无法将算法+医学知识和软件工程结合成一个合力。
    尽管他们拥有当时最先进的AI和算法。可是工程师说：“那帮博士们写的东西都没有用。整天不知道他们在干啥。”
    于是他们的AI医疗产品一直没有落地。

另外一个和我们日常开发比较接近的例子

    国内金融行业恒生、赢时胜老一代的Delipe+存储过程系统处于向新一代微服务架构转型。但几乎全部陷入焦油
    坑之中，甚至在客户现场并行数年，因稳定性、性能等原因不能上线。

    从过程上，他们的研发经历了7~8年大概3个阶段 
        1，自力更生。delipi+存储过程原班人马转型微服务架构。
        2，使用外援阶段
        3，回归自力更生
    
    在第一个阶段，他们用delipi+存储过程原班人马转型微服务架构。做了几个架构决策
        a，横向按照流程阶段划分为几个微服务，纵向根据业务场景、行业扩展分为几个微服务。
        纵横大概都有10+，总计接近180+微服务模块。
        b，复用源于c++核心组件，微服务架构只是调用接口，和银行微服务架构对接兼容。
        降低改造点、风险；又满足行业发展趋势。
        c，多个组件之间以webservice通讯。 

        结果是IO多，内存占用高，系统容易崩溃。微服务模块多，运维响应慢、故障响应慢、需求
        响应慢。
    
    于是进入第二阶段，招大量大厂专家来解决问题。
        大厂专家引入了流程编排架构体系。好处是
        1，容易把大的复杂业务拆分为N个小的原子积木。根据需求灵活组合起来。
        2，流程可编排容错降级、重试、告警等等机制。对业务逻辑透明。对改造比较友好。 
        不过大厂专家大刀阔斧也仅仅到此为止。因为主流程业务密集度低、流程长适合这个技术。
        清算、台账（会计科目）……等子组件业务密集度高，流程短，流程编排没什么作用。
        涉及到金额、一致性要求很高、改造风险大…………这个阶段，大厂专家开始抓客户满意、精力投入到客户
        身上，而不是架构改进。

        1~2年大厂专家也下线。

     当前是第三阶段，又启用了恒生土著领导。
        操作上看不清楚，风格是更保守的。
        应该在方向上迷茫不知方向的。

     赢时胜XX系统也是同样的问题，因为稳定性和性能问题，在客户现场并行数年不能上线。
        他们从18年开始做，迄今为止6年，换了四波人。
        24年的时候，原团队解散、打散。换另一波团队来负责；项目的组织架构从A事业部换到B事业部。
        
        1，他们架构问题相对较少，用的是纯粹的springcloud微服务。微服务划分粒度也不是那细，
            如果大规模改造，协调和组织架构层面的掣肘问题不那么明显。
            陷入困境纯粹是因为系统各方面复杂度过高造成的。

        2，核心业务本身比较复杂
            有8层+高耦合的处理逻辑（交收日/交易/交收路径/账号类型/交收账号/交收模式/抵扣模式/路由模式，交收明细、交收汇总）
        3，他们核心的业务代码，没有抽象，直接针对具体业务场景，并且彼此混杂。 
            交收日：香港/大陆/XXX，节假日/非节假日，T0,T1.....
            交易：中登/直销/利息/XX费
            交收路径：无/分段式/分段+特殊
            账号类型：销售户、渠道户、过渡户、归集户、机构户……
            交收模式：逐笔，产品合并，渠道合并……
            抵扣模式：账户抵扣、交收明细抵扣、充值明细抵扣……
            路由模式：产品路由、渠道路由、5要素路由……
            ……
        4，技术复杂度耦合
            4.1 没有使用异常，使用异常码。导致以上N层每一层异常对上层不透明。
            4.2 各种参数检查、错误和上面N层业务耦合、必须在运行时能够清晰明确知道
            4.3 高性能要求 海量数据，内存处理
            4.4 强一致性要求、不允许一分一厘的金额错误 

        改进方式不难，针对其中最复杂的一个模块，做了如下改进。其他次复杂的模块照抄
        1，去异常码，使用异常：确保业务代码聚焦业务，简单清晰。彼此低耦合。
        2，开发批量底层框架：确保高性能、高可靠、高一致。预留业务读，写，处理扩展接口。
        3，核心针对抽象编程
            核心针对抽象编程
            各业务场景继承扩展核心接口、编排组合各种扩展的具体实现。

            比如中登业务继承基类、引入交收路径组件、路由组件、映射到账户和交收日。
                而费用业务继承基类，不引入交收路径直接对将费用结算到渠道户或者机构户。
            总之，以线（流程编排/模版方法）为纲，组合原子能力的各种扩展。
        4，遗留代码迁移：
            业务逻辑不作改造，
            迁移到新架构各个组件相应的功能位置。
            加强单元测试，确认流程跑通。新架构流程是清晰的、结构是合理的、跑对跑快相对比较容易。
        大概花费了1~3个月就完成了核心改造、新老系统对账比对验收。

        不过，这样改造只能确保跑对，不能说架构上是合理的。
            1，微观代码依然是不合理的。
                是针对具体业务进行编程。
                新需求需要代码改造才能实现。不能构通过组合、配置等方式实现。
                在反复的迭代下，局部复杂度高的依然非常难维护。难以理解。
            2，架构目标中的一套系统支持券商和银行的设计不可能实现。

        因为赢时胜和恒生基本的开发模式是
            1，业务、产品、开发、测试被效能流水线驱动。
            2，所有需求拆分为按天计算的需求。在流水线上滚动，验收。
            3，它不是基于完整设计的，而是基于碎片化业务的。
            4，它实际的运行模式中开发是不可能识别需求合理不合理、也不可能做什么设计。
                “有经验”的开发评审产品需求的唯一依据就是有详细到我对着就能直接编码。
                公司也鼓励按照产品设计做编码，有错去改需求设计。 
            5，而产品人员是不可能有啥架构设计、抽象能力的。
                他不可能意识到交收路径和具体交易之间需要设计撮合引擎。来实现58种优先级计算模式的配置。
                他只能提供5万字的需求文档，散落在文档的各个步骤中描述各个场景应该怎么个映射逻辑。
            6，所以，几轮流水线需求迭代以后，代码必然是看不懂、改不动的。
        
        这也是大多数软件开发公司的开发模式的通病，为什么恒生和赢时胜会这么明显呢？
            1，通用性要求强
            2，业务复杂度高
            3，性能要求高
        而大多数公司的业务，大多数都是业务流水的CRUD，至多流程复杂一点。加个流程编排能解决一大半。

        改变这种状态的方式本章节提到的
        1，各个转业角色有概念完整性视图
        2，各个专业根据概念完整性视图提出设计提交物。 
            架构师：4A+各角色划分+制品包规范
            业务专家：ER模型————业务模型沉淀为ER设计，实现可扩展，可配置、可组合。日常业务避免对开提需求。
            技术架构：批量高性能的规范。
            XX引擎主程序：
                1，根据ER中对应模块配置表结构和词典实现对应组件，可解析执行对应配置，处理业务流水。
                2，给出对应组件的架构设计（对象图、时序图、状态图）
            YY技术组件：实现业务无关的，通用的技术能力，比如缓存，通讯、校验、锁……


架构设计本身，就是为了实现各个专业角色彼此关注点分离、0知识协作、彼此低耦合、高内聚。其次才是实现技术上、工程上的低耦合、高内聚。
