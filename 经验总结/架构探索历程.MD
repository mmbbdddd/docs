# 架构探索历程

**08年以前**

想成为架构师。学框架，看理论，模仿。

**09~12年**

经历了十几次架构重构。最后搞出了一套微内核风控系统，任意行业、任意规则、任意数据和技术框架都能适配。第一次感觉到——有些东西是不变的，抓住了就能通吃。风控虽然复杂，变化无非是数据和逻辑，分别可以用el和脚本引擎解决。这两种工具可以解决这两类的任何变化。

**14~16年**

改进工作流框架PC，对流程引擎，状态机的掌握。解决了任意业务流程怎么变的问题。

**17~26年**


先是认清了软件架构的本质——就四个东西：事物、关系、变化、不确定性。搅在一起，复杂度必然爆炸。架构的全部意义，就是控制这个爆炸。压住混沌，给涌现留空间。

怎么控制？怎么设计？怎么不混沌？怎么涌现？

带着这四个问题，回头翻自己做过的项目。先看水平垂直划分。拆完之后有个悖论：局部简单了，整体更复杂了。工程可行了，工程效能下来了。拆不是免费的。

做项目的那些年，也跟着业界潮流用过DDD。理念确实好。但看了一圈落地的情况——CQRS、COLA、一层套一层的分层——很多人用完系统比不设计还乱。当时以为是落地手段不成熟。后来才想明白，不是落地的问题。是DDD的根子有问题。它假设领域稳定，但业务永远在变。对变化的东西建模，刻舟求剑。

DDD这条路走不通。那有没有更硬的东西？数学。群论。
软件无非输入一组数字，输出一组数字。本质上就是矩阵运算。把矩阵结构用逻辑表达出来，那是写代码。为什么不能反过来——用数学指导逻辑的结构设计？

但群论本身的复杂性把我折腾晕了。醒悟过来：软件工程首先是工程，你得让普通人能用。太复杂，就工程化不了。否了这个方向，顺便否了微分那套。转而看拓扑。

以拓扑为工具。为嘛呢？参考西方的成功经验，他们的架构图某个阶段也叫做拓扑图。他们为什么会找这个工具呢？

我试图还原他们分析问题的历程，最终得到一个思考方向：完备，能表达任何问题。工程化，效能最高、复用最大、工作量最小。高可靠，高灵活。

怎么达成？把任何问题向一个平面投影。投影重叠的部分，就是可复用的——叫组件。整个投影平面是容器，确保完备。容器对里面的代码有正交增强能力，最大化降低工作量，提升可靠性。最后用事务脚本组合组件，表达业务，保证一致性、可靠性、可容错。

我似乎重新发现了JEE架构哲学。

可是，为什么JEE理念上这么完美，软件质量还是烂？腐化的系统还是到处都是？

问题回到了DDD——可DDD也没有解决问题。

我翻出这些年做风控、做流程引擎、做大大小小项目的经验。早些年，面对一个陌生领域，我第一反应是啃业务。学大量领域知识，沉淀出领域模型。这条路我走通过很多次。但每次都脱一层皮。

走得多了，确实顺了。可做完之后越来越觉得不对劲——这些代价，好像不必付。不需要学那么多领域知识，也能拿到领域模型。

反过来，学太多反而是累赘。

很多次，我提炼出了模型，但在这个领域干了十几二十年的业务专家，自己却说不清。模型不是从他们嘴里问出来的。

从设计哲学上想：一个模块越依赖另一个模块，扩展就越难。那设计方法本身呢？越依赖特定领域知识，出来的东西不是越脆弱吗？

关键是正确的设计方法论。

于是我顿悟了。流程引擎、聚合根、事件风暴——这三样东西有机结合起来的意义，突然通了。

我重构了DDD，让它更容易落地。

这后面我在很多系统中，实践了这套方法论、无一败绩。得心应手；但是也观察到了一个现象，理论上这套方法论是完美的，也可以结合各种具体的技术灵活适配，可是却都要反过来解决各种技术的副作用。

否则，理论只能是理论，无法工程化、可复制。

| | 复杂度 | 弊病/收益 |
|---|---|---|
| 概念、理论、符号 | 无 | 不落地/零熵 |
| 表达式 | 低 | 主机有限性限制 |
| 函数 | 低++ | 学习成本、心智负担高、不直观 |
| 对象 | 中 | 主机有限性限制、有状态 |
| 模块/库包 | 中++ | 主机有限性限制 |
| 应用 | 高 | IO错误/分布式 |
| SOA/微服务 | 高++ | 高协作成本、高IO |

到这里，自然逼出一个更底层的问题：**怎么用一堆不完全可靠的组件，搭出高可靠的系统？**
到这里，自然逼出一个更底层的问题：**怎么用一群有缺陷的，但是都有专长的人，搭出高可质量软件？**

工程实践中总结了一套理论和方法，结果发现重新发现了关注点分离。
