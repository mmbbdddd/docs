# 架构探索历程

## 08 年以前

想成为架构师。学框架，看理论，模仿。

## 09～12 年

经历了十几次架构重构。最后搞出了一套微内核风控系统——任意行业、任意规则、任意数据和技术框架都能适配。

第一次感觉到：有些东西是不变的，抓住了就能通吃。风控虽然复杂，变化无非是数据和逻辑，分别可以用表达式引擎和脚本引擎解决。这两种工具足以应对这两类的任何变化。

## 14～16 年

改进工作流框架 PC，深入掌握流程引擎和状态机。解决了"任意业务流程怎么变"的问题。

对于大多数应用类业务，复杂多变的是流程（线），流程上每个节点无非是增删改查（点）。点的变化比较容易应对，而线的变化耦合太多，很容易造成全局紊乱。

通过流程编排——向下对组件抽象合理、向上对业务编排适配——可以解决大多数应用类问题。

对风控等极少数节点极为复杂的系统，则做引擎化策略，屏蔽单点的巨大复杂度和可变性。

## 17～26 年

### 本质认知

先是认清了软件架构的本质——就四个东西：事物、关系、变化、不确定性。搅在一起，复杂度必然爆炸。架构的全部意义，就是控制这个爆炸——压住混沌，给涌现留空间。

怎么控制？怎么设计？怎么不混沌？怎么涌现？

### 拆分的悖论

带着这四个问题，回头翻自己做过的项目。先看水平垂直划分。拆完之后有个悖论：局部简单了，整体更复杂了。工程可行了，工程效能下来了。拆不是免费的。

### DDD 的困境

做项目的那些年，也跟着业界潮流用过 DDD。理念确实好。但看了一圈落地的情况——CQRS、COLA——往往一层套一层，比不设计还乱。

这当然不是 DDD 的问题，是使用 DDD 的人没融合《人月神话》手术刀团队的意思——DDD 在设计上将复杂度从技术收敛到业务，从业务收敛到模型，集中到一个点上；但在工程组织上，也必须集中到一个点上，让少数的人来解决，才是复杂度最低、质量最高的。

这种事，得管理层决定。大多数研发公司管理层要么找不到这样的人——既懂业务、能抽象、懂设计、能编码落地。

有没有更低要求的、可工程化的手段？大多数软件按部就班按照工程步骤执行就行？

### 转向数学：群论

DDD 这条路走不通。那有没有更硬的东西？数学。从群论等理论寻找灵感。

软件无非输入一组数字，输出一组数字，本质上就是矩阵运算。某个领域一定对应一个特定的矩阵，这个矩阵可以用输入和输出通过数学手段计算出来。把矩阵结构用逻辑表达出来，逻辑上就是应用架构设计——并且它理论上应该是最完美的，优雅、可维护。

但群论本身的复杂性把我折腾晕了。醒悟过来：软件工程首先是工程，你得让普通人能用。太复杂，就工程化不了。放弃了这个方向，顺便否了微分那套。

### 转向拓扑

为什么以拓扑为工具？因为吸收了刚才的教训——最好不要自己漫无目的地瞎琢磨，先吸收过去的思路会更好。

我试图还原前人分析问题的历程，最终得到一个思考方向：存在不存在一种拓扑——完备，能表达任何问题；效能最高、复用最大、工作量最小；高可靠、高灵活？

经过一段时间的实践思索，发现还真存在。

把任何问题向一个平面投影。问题足够多，就形成了一个斑驳的投影。投影重叠的部分，就是复用性高的；投影稀疏的部分，就是按需定制的业务逻辑脚本。

我似乎重新发现了 JEE 架构哲学：

- **浓重的** —— 即 JEE 组件
- **稀疏的** —— JEE 事务脚本（EJB 接口扩展）
- **整个平面** —— 容器

组件确保业务开发逻辑上是最精准、工作量最少的；容器进一步正交提供了分布式、高性能、高可靠等企业级特性。

### 反思：为什么系统还是会腐化？

需要考虑的是：JEE 理念上这么完美，为什么诞生几十年之后，应用软件质量还是烂？腐化的系统还是到处都是？

甚至 JEE 之后诞生的 DDD，也没有改变多少。

仔细探究 JEE：它并没有侵入业务层，只是把业务层的复杂性全部打包给了事务脚本。在业务层之外，它提供了可复用的组件。所以，它没有办法降低业务层的复杂性，只能降低技术层的复杂性。

JEE 的发展中，Spring Cloud 将这一切做到了极致——通过容器和组件设计，几乎屏蔽了一切技术和分布式复杂性；对大多数业务系统，只剩一层简单的接口契约和配置变化。

### 审视 DDD：理念完美，落地模糊

DDD 在理论上是完美的：

1. 将系统复杂度从技术聚焦到业务、从业务收敛到模型，缩减到一个点
2. 通过事件风暴等手段，实现领域的提炼和论证
3. 通过战略设计，实现模块的分割
4. 通过战术设计，实现编码的落地

可是仔细落地就发现：它似乎什么都说了，却似乎什么都没说。具体做事还是不知道该怎么做。

比如：

- 事件风暴的产出物是什么？
- 这些产出物和下一步的战略设计、战术设计有什么关系？
- 这些产出物和公司的规划、战略有什么关系？如何衔接？

我翻了 DDD 这些书几百遍，没翻到答案。

### 问题域就一定存在吗？

我质疑 DDD：任何问题领域就一定存在领域解吗？

思索的答案是：未必存在。

那如何分辨问题域是否存在领域解呢？

答案是：无法判定。

既无法判定、又不能确定存在；又没有给出清晰可落地的方法论，只是给了一个愿景式的、理念上正确的方法论——对工程实施而言，无异于盲人摸象。

我更愿意从真正的工程实践中去总结。

### 从实践中提炼方法论

我翻出这些年做风控、做流程引擎、做大大小小项目的经验。

早些年，面对一个陌生领域，我第一反应是啃业务——学领域知识，沉淀出领域模型。这条路我走通过很多次，但每次都脱一层皮。

走得多了，确实顺了。可做完之后越来越觉得不对劲：这些代价，好像不必付。不需要学那么多领域知识，也能拿到领域模型。反过来，学太多反而是累赘。

很多次，我提炼出了模型；但在这个领域干了十几二十年的大量业务专家，明明专业知识、细节懂的比我多，却提炼不出来模型。

我觉得存在一些根本的限制，不是智商的问题。

从技术耦合的基本逻辑上看：一个模块越依赖另一个模块，耦合便越强。即使是设计过程本身——依赖特定知识，设计出来的东西越耦合这些知识；依赖的越多，耦合的可能越多。

但是，也不可能完全不依赖，凭空想。

正确的方法是：了解一些 → 总结归纳抽象 → 再找一些验证 → 找出改进 → 反复归纳，反复论证。

### 归纳论证什么？

不是任意的业务细节。

第一是**流程**。第二是**步骤的策略词典**（我常常叫业务词典，即此步骤的业务变化）。

然后针对这套抽象的流程和策略词典进行架构设计和落地。

流程衔接公司业务战略、客户、业务流程、架构设计；策略词典衔接具体业务、领域驱动战略和战术设计——灵活适配、高性能、高质量。

之后 7～8 年，在大量项目中实践、完善这套方法论，得心应手，无一败绩。

### 发展：副作用与关注点分离

理论的东西，虽然不拘泥于任何具体技术和手段，但工程落地本身必须结合具体技术和手段；也一定存在它们和理论的不适配——即技术、工具的副作用。工程落地上要有手段落地，也要注意消除这些手段的副作用。

当然，除了副作用，它们也一定引入了额外复杂度（即偶然复杂度）。首先要确保在解决问题的情况下选择合适的复杂度——能低则低，适当预留发展空间。其次要在设计上考虑消除这些复杂性的工程手段和管理手段。

| | 复杂度 | 弊病 / 收益 |
|---|---|---|
| 概念、理论、符号 | 无 | 不落地 / 零熵 |
| 表达式 | 低 | 主机有限性限制 |
| 函数 | 低++ | 学习成本高、心智负担重、不直观 |
| 对象 | 中 | 主机有限性限制、有状态 |
| 模块 / 库包 | 中++ | 主机有限性限制 |
| 应用 | 高 | IO 错误 / 分布式 |
| SOA / 微服务 | 高++ | 高协作成本、高 IO |

到这里，其实是解决了一个基本问题：**怎么用一堆不完美的、有专长、有缺点组件，搭出完美的系统？**

### 团队维度：关注点分离

但还存在另外一个大问题：我个人再牛，也只是一个人，不是团队。我不可能干多少活，精力和能力有限，也不可能什么都懂、真正解决所有问题。

如何让团队每个人在软件工程中都发挥最大的作用，同时消除他们的副作用？

在 YSS 新一代的架构探索中，我发现即使第一版的架构很完美，随着迭代，还是在快速腐化，很快维护不了——我不可能天天盯着。
