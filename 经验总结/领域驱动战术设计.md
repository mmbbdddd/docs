# 战术模型概念

    任何一个业务领域未必有领域模型。
    但编程本身却肯定、必然有领域模型
                                        ——王林

无论多复杂的领域，究其代码，只有如下几种角色。
* 事件
* 聚合/实体
* 策略对象/值对象
* 上下文
* 防腐层

实体即事件中的Payload，是聚合的处理对象。例如对用户系统，实体是User，聚合是UserService。
聚合/实体在时序图中是最左边那个竖线的策略对象。

策略对象/值对象 是时序图中其他竖线的策略对象。 例如UserTypeService,AuthService....
代表可以玩出的花样。如不同的用户类型有不同的计费方式，或者支持多种的登录认证方式……
其中策略是能力，值对象是配置。可以单独只有策略，如果还有值对象，代表这里有变化，策略进化为工厂。

最典型的例子是Dubbo，本来是个简单的RPC框架，做个接口代理，完成IO通讯就好了。
结果凭空创造出了很多的值对象，例如容器、序列化、服务发现、容错、负载均衡……大概13个之多

上下文是日常开发中最常见又最不常见的概念，大家天天说，但很少用。
技术上讲呢

    1.     上下文是全局的抽象
    2.     上下文是弱类型的

一般的设计原则要求代码本身要求是单向依赖的，但是有些问题本身就是自指的。如果反申依赖不可避免。
可以将自我依赖转移到上下文上，其他对象干净。

第二，其实是最常见的，它里面什么都能放，都能拿。极大扩展系统的灵活性和扩展性————其他部分要求强类型，单一职责。

总之，如果反模式不可避免，就集中到一个点上。
# 其他精髓

DDD战略模型，相对来说，就不那么精髓。

他的CQRS，EDA，也不错，但容易滥用。

所以，DDD最关键的，是理解他思想的精髓

    复杂度不可控，则集中于主要矛盾，主要矛盾的主要方面，尽可能收缩到最小的点
    在工程上，选派最精干的人设计、开发；确保质量和效率
