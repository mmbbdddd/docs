# 流计算Spark

2012年做风控系统，有一天系统半夜宕机。宕机的原因是1%的慢规则消耗了系统99%的线程资源。

解决优化措施有3个

1. 架构完全异步化
2. 超时熔断降级策略
3. 让慢规则计算的快

慢规则基本由于过大的数据量、或者过慢的IO导致的，比如我们要计算的数据量超过几万条甚至几百万条、或者我们访问了某个外部、远程的不可靠的IO。

同步的线程会被阻塞，完全浪费在等待中。

异步化架构确保慢操作线程立即被释放，只在结果回调时notify请求方接口/线程。几乎不会浪费系统线程（线程池）资源。

超时熔断机制是为了确保在实时线程中，请求线程被await，但回调事件并没有发生的情况下的资源安全问题。

1、2这两种方案，可以确保系统的安全，但伴随的往往是降级、较慢的规则执行速度……比较差的业务体验。

比较彻底的解决方案是提供海量数据的实时计算引擎。

在2012年以前,当时还没有Spark/Hadoop也并不为人所广知。我们探索出了另外一种基于内存+事件的实时计算引擎。
    
    简单说呢
    1，在Redis中存储指标
    2，每个指标的计算逻辑被（Create/Destory/Reset)事件触发
    3，Create事件代表了订单的发生、Destory事件代表了订单事件窗口过期、Reset发生在系统重启等阶段是对指标的修正

看起来这套架构挺优雅，其实一点也不。

在性能上，它很不优雅，IO是3 * N * M的。一点没省。（N是数据量，M是指标数） 

好的设计必须

    1，合并IO，
    2，批量计算。
可是，这两者会伤害实时性、并且让简单的架构模式变得非常复杂。

即使我认为很丑的Hadoop，也不过是3 * M * N的。（但Hadoop不是基于实时计算的）

后面看到Spark的RDD后。佩服的五体投地。

Spark的模型很优雅。

    1，RDD本身只是一个数据集抽象。代表内存一小块数据 
    2，RDD支持流式计算语法，计算函数很丰富，很灵活，比Hadoop的MR要不直到高到哪去了
    3，RDD本身透明分布式，支持海量数据
    4，RDD的Datasource抽象屏蔽了RDD的数据来源，可扩展FileStreamSource、KafkaSource等

RDD的模型好在哪里？它是DDD的，它直接假设了一个最理想、最优情况下的模型，支持无限数据、无限算子扩展、最低IO最高性能。然后扩展
支持外部任意的场景。

我的呢，感觉是在不停的为各种特例情况打补丁。我最初以为实时计算的核心问题是计算————实际上，到周发现是数据问题，是IO问题，为这个错误的设计不停打补丁。
很丑，很蹩脚，但当时不直到问题在哪里。只是感觉很纠结，既想兼容内存，又想兼容性能、但感觉彼此之间有很大的鸿沟，不能同时兼容。

RDD就完全没有这个问题。 

    Spark完整链路：Kafka → Spark Executor 内存 → Shuffle 落 HDFS → 结果写入 Hive/HDFS → 再启动 Spark SQL 查询；
    其中有多次落盘，理论上不是最优。
    现在Doris等架构，可以完全内存MemTable避免Shuffle阶段的IO消耗，性能极高
    但整体架构优雅程度、简单程度，Spark是天花板----考虑到当前大数据计算80%场景是Spark----不这么做更多是兼容性和必要性

# 开放接入平台

2014年，支付宝金融交换系统重构后的业务流量迁移主要靠的是开放接入平台。

它把支付宝重构后，散布在10来个部门、几百个微服务系统的几千个业务的配置平滑迁移到新系统中。

    页面参数配置==>分布式配置推送==>测试验证==>测试报表==>上线
    
    金融交换网关复杂和所有外部系统对接，包含银行、基金、保险……对外对接各种通讯协议、加密解密协议、
    报文协议……对内只有业务码+RPC+Map。是一个防腐层业务网关系统。
    
    重构前的金融交换是70+个微服务系统。 有些是机构性质维度的：比如银企直连、银联；有些是产品性质的，
    比如：卡通。有些是客户性质的：比如建行，招行，农行……
    
    重构后，大概6个子系统：组合，信息，流入，流出，批量，超网。

开放接入平台V1是一个老阿里做的，目的是自动化迁移。大家开玩笑说这玩意虽然是自动化的，但是一个接口需要开发一次，
每次1个月。人工迁移才半个月。所以大家都不爱用。

我分析了一下，它有它的好处，自动化，可靠性。人重做的时候会漏东漏西。

不好的地方呢，是架构太僵化，开发成本太高。

当时阿里流行能力复用、架构复用。阿里的架构师呢，就抽象了很多Ability组件，比如卡通Ability，异步Ability，HttpAbility
……等能力，通过对这些能力的组合，得到了新的能力，新的能力可能就是业务。

老的能力的封装呢，是一坨Java代码；能力的组合呢，也是一坨Java代码。
但是能不能组合呢，组合后能不能用呢？都依赖于人的梳理和测试验证。在事前并不太好确定，很多时候是写完测完才知道。

V2的架构，我完全颠覆了这种僵化的设计。我设想中

1，开放接入平台应该是模式驱动的，多专业角色的、可配置的平台
2，开放接入平台应该流程可灵活编排的、不同模式编排不同页面，系统，测试案例集。
3，开放接入不是所有角色的任务都必须交给开发去开发、特定角色很重、被瓶颈卡死的系统

基于这样的愿景，设计了如下架构模型
    
领域模型

    模式HTML ：特定模式、特定角色输入配置的页面。只html语法。没有其他复杂的语法。button提交后结果为map
    Map     ：特定模式的入参对象，同意存放在Map中。
    System  ：特定模式下，要推送的系统ID
    Template  ：系统配置模板  
    TestSuite：测试案例集   
    ProcessFlow:编排以上， 构建、推送、测试特定模式整体配置的工作流。一个xml文件。

这样，一个模式由1个流程编排xml文件+几个页面+几个配置文件就搞定了。 所需要的开发技能只有html+freemarker+jdbc。

V2架构下，开放接入平台1年就帮助部门完成了所有的迁移工作。架构设计获CTO最佳设计奖，晋升1P82P7.

这个系统，和超网一样，是支付宝几百个系统中唯2简单优雅的系统。我从阿里毕业很多年后，尚且有不知道我的后辈夸赞架构优雅。

这个架构好在哪呢？它设计都是极简，**都没超过小学二年级的水平。**

# 批量风控 

大多数核心联机业务系统，**如果业务很复杂、步骤很长**，那么用**Pipeline或者流程编排组件**，将复杂步骤切分为几个积木组件。就可以完成标准化
积木话的架构设计。做到很好的架构隔离、可维护性、可扩展性。例如Jenkins的流水线架构，阿里的cola。

如果**局部的点，很复杂、或者性能、可靠性要求很高**、则对局部的点做工厂化、引擎化的设计，也大概能解决问题。如清算引擎、撮合引擎、对账引擎等

以上种种，仅仅根据业务侧的复杂性做设计和抽象就可以了。

比较有意思的是**数据量极大、性能要求很高**的点，它的解决方案不仅仅要包含业务侧的，还要包含技术侧的。

比如券商的投资监督系统，是一个批量的、数据量、计算模式极为复杂的风控系统。

    最初，老版的是C# + 存储过程架构的。天然性能很高、一致性很高。
    新版，是微服务架构的，要支持信创，不能用存储过程。
    要达到，甚至超过原有的性能，必须走内存计算引擎的路子。
    但，这个新架构上限之后，经常OOM溢出；要求2H的日终任务往往8~24小时跑不完。

我接这个系统后，将这个系统性能提升了10倍，到40分钟；并且内存资源可控，不再会OOM。关键是做了一个抽象FRD。

    FD =  一个或者多个产品、日期关联的数据集
    R  =   FD关联的规则集。

流程呢，是
    
    1，加载产品+规则+日期
    2，构建FRD执行计划：产品*产品*规则*日期
    3，调度每一个FRD执行计划，并执行计算
    4，汇总执行结果

1 4 不会有问题。 问题在哪？在2 3


    1. FRD执行计划笛卡尔积过高，导致GC
    2. FD范围过大，导致内存OOM
    3. FD计算完成后，内存回收不够快，导致OOM。
    
怎么优化呢？

    针对1，对几十万亿的计算任务进行分片计算。确保每个分区不超过一定size，
    每个分区之间sleep固定秒数。不做这个，往往会YGC几个小时。

    针对2，引入本地缓存组件(duckdb)，每个FRD设定最大内存消耗，超过的都推到堆外缓存上。
    利用这些组件的扩展函数扩展算子。

    针对3，针对F进行排序、调度，确保数据相关性任务分布在同一块主机。计算完毕后内存立即被释放。

 
其实：如RDD一样，几乎所有大数据量实时计算的框架，核心都是数据模型的抽象。如Spark的RDD。如投资监督的FRD

这个FRD的抽象好在哪呢？

    1，向上，透明扩展产品、规则、计算日期范围。是个高度产品化的业务架构。
    2，向下，透明内存调度、资源管控。是个高度稳定、可靠的技术架构。

# XX新一代清算重构

A公司新一代V7清算系统，蹉跎了5年没有研发成功。

他们上一代，其实叫做V4.5。是业界占有率最高的系统。

中间V5 V5.5 V6都是夭折的

技术团队换了3波血、负责人调了2轮，总经理都换了1次。

清算看起来并不是一个业务非常复杂的系统，为什么如此难产？

其实，宏观上看，他们整体架构设计很正确。

    背景知识：
    清算系统业务流程大致步骤7步：导入、清算、交收、支付、对账、台账、凭证 
    前5步是必须的，后2步是优化项，可以忽略。

他们的设计
    
    7个步骤分为7个微模块
    每个微模块采用引擎化设计

如此一来，每个模块其实任务相当简单。
    
    导入：原始交易导入到原始表
    清算：原始表到标准表，本质上是不同周期和流程的分离
            如息/月结，对象是账户+计息规则
            如费/日结，对象是交易+分润规则
            如罚/日结，对象是交易+条件，如撤销交易，久悬户等
    交收：分两部
            1，交收明细：从对象+规则产生出不同账户+日期+金额的交收明细、确保一致性、可靠性
            2，交收汇总：按一定的合并规则，将金额收支明细汇总到特定账户，减少收付次数
    支付：将交手汇总收付出去。
    对账：获取银行流水，对首付进行对账
    凭证：使用会计科目对资金变化记凭证。

其中较为复杂的是清算和交收。A公司正是交收模块在复杂产品、交收规则下帐算不对、不准、系统容易崩溃、性能不达标。
代码完全失控，开发看不懂，不敢改。

根因，代码复杂度过高

    业务复杂度：产品+机构+渠道+账户+交手日+节假日+账户类型+.....10多个业务要素的复杂性叠加，每一种要素可能几个甚至几十个变化。
    性能：数万产品、数千机构、数千渠道.......数十万交易明细的笛卡尔积，海量数据，秒级性能要求。如果使用内存会爆，使用缓存会有并发一致性问题
    一致性：1年交易1丝1厘不允许错
    技术复杂性：使用异常码而不是异常，导致每层异常复杂度是上N层的叠加
    
解决方案呢？

    1，使用异常码，避免异常处理爆炸，聚焦主流程，异常全部回滚/上下文错误
    2，所有配置规则统一为2类
        配置：产品、机构、渠道……或他们的组合，统一为一套表达式
        优先级：同一交易，所有配置统一渲染，统一优先级处理。产出是同样标准化的数据

输入数据  ==>N套配置同时执行  ===>执行优先级选择  ===>输出数据

杜绝了硬编码。

如果不这样呢，就是业务复杂度，技术复杂度，异常等等复杂度的叠加。没来一种情况，代码跟着调。

总结论述
    
    流程的标准化：
    配置的标准化：统一配置表达式
    数据的标准化：输入  输出



# 架构之美

架构的目的是，控制复杂性，提升确定性，可能性空间。

为了控制复杂性，它必须是不变的，化变化为不变的。尽量少实体的，尽量少关系的。确保他们是MECE的。

但架构又不是死的，而必须是泛化的。抽象的，蕴含极大的可能性扩展。

通过这种抽象+不变的组合，组合出前边万花的业务，包含

    - 流程变化
    - 数据变化
    - 策略变化
    - 配置变化  

当然，在变化中也有不变的规律。比如批量中对数据集的关注。以及他们融合的规律，比如FRD。
