# 不约而同的困境
2022年我所在的运营事业部估值、清算、投资监督.....等新一代系统陷入到焦油坑中，很多在客户现场并发数年无法上线，或者上线反馈不好，问题频出。

于此同时，资管事业部的新一代的o32、o45也是类似的情况。

同年，赢时胜新一代V7微服务架构清算也陷入同样的境况，从2019年开始研发，到2024年换了3波研发团队，2位部门事业部经理。

为什么他们新一代微服务架构重构都陷入了这样的困境，和阿里的中台运动的失败有没有相关之处呢？

# 恒生新一代大事记



1. 18年开始转微服务，以老恒生人马为主
2. 21年开始进入收宫阶段，但开始频繁社招互联网大厂架构师
3. 23年老恒生失去技术主导、重视外来资源
4. 25年外来势力失势，回归老恒生
……最近的情况我没有关注



以我最了解的恒生和运营事业部为例，他们是核心业务外最复杂、最基础的业务。所以从他们开始试点。大概从2018年左右开始。此前他们是Delphi+存储过程的架构。现在随着甲方转微服务架构和信创要求，他们必须跟上。


第一个阶段，项目特征是

1. 恒生原班人马
2. springcloud互联网成熟技术架构微改造为作为脚手架
3. 横向按功能模块拆分、纵向按行业、业务模式作拆分，估值拆到200左右微服务。
4. 复用Delphi/c/c++等业务核心技术资产，通过websevice和新系统进行整合。

这个架构的好处是
1. 老代码复用高、投入和改造比较小、业务风险低
2. 新技术是在老技术上套一层皮、和行方技术架构体系适配兼容性高

坏处是
1. 微服务多、io调用多、webservice序列化多。 性能低、内存占用高、可靠性低。
2. 部署复杂、部署成本高
3. 需求变更响应慢
4. 线上故障定位慢、修复慢
5. 很多客户现场并发数年达不到客户要求

进入第二、三阶段 发生了几件事

1. 招聘阿里的技术专家、对问题进行改进
2. 否决了去webservice的架构改进方案（优化io，内存，序列化）
3. 采纳了基于流程编排的架构改进方案
4. 采纳了合并部署，降低微服务数量的架构改进方案（优化部署成本）
5. 流放了原恒生技术主管，重用阿里技术主管

这几件事我的分析是这样的

12是在原恒生领导的主导下，吸纳了外来外来和尚的建议，并主导完成的。小步迭代，风险可控，缺点是没有全局方案，看不到尽头。

后来阿里某和尚越级汇报后，技术线基本以他为主，开始主导推进以流程编排为核心技术特征的技术改造。

这个技术组件的好处是他是一个宏观架构组件。可以将一个非常复杂的业务端到端切分为N个简单的功能组件，并发推进完成。另外，流程编排本身的积木话组合组件的特征，也可以让他轻易的适应大的宏观流程的变化。所以，我猜测恒生的领导因此重用他，试图获得更完整、清晰的改进。

但阿里主管在做了4的技改之后，开始发力客户满意、客户服务。而不再发力底层架构改造————涉及到清算、核算、会计等一致性要求更高、业务含量更重、风险更大，外来和尚业务积累和经验更少。

大概经过2年的蹉跎后，恒生估值6.0 和6.5双双无疾而终。阿里高管失去信任，恒生领导重新主导

# 对恒生新一代项目的反思

恒生的核心问题是




- 1. 团队文化过于重视业务、对技术发展关注不足，导致技术架构突变后掌控能力不足（尤其是中层管理，基本脱离一线开发，这和赢时胜的高层截然不同，YSS高层从秘书长、总经理到总监甚至参与一线产品讨论和代码开发，并且始终对新技术保持关注和跟进）
- 2. 金融业务导致组织文化、管理文化必然是以稳为主、很难胜任突变
- 3. 过于复杂的业务、不成熟的技术决策……综合产生的复杂度超出开发团队的掌控
- 4. 裁员压力等等……导致新老团队很难进行技术、业务的无缝融合，进行风险极大的技术改造

其中 1 2 4我都看到了解决方案。3 4是共同的，比较难以克服的问题。
比如 1 YSS他们的估值业务研发是相对顺利的，（他们估值业务技术总监设计和编码造诣极深），但清算新一代研发并不顺，这个事业部他们缺乏这样的大咖能拿住局势，这个领域他们最专业的不过是清算领域的架构师（按能力大部分架构师都是技术专家，算不上架构师）。
比如 2 YSS他们管理文化就很不错
4也有办法克服，办法后面在YSS清算系统重构的里讲
最核心是3  YSS他们新一代清算系统也掉进坑里，2019年开始研发，研发5年无法上限，完全换血了3波技术团队，事业部负责人换了2波；依然无法改变客户现场UAT并行数年无法上限的问题。（最直观的，帐算不对，代码一改就崩，越改越不稳定，团队中没人能维护这个代码————这代码是新的，甚至还没上线过，没接过新客户需求迭代已经如此了）


# 赢时胜新一代的问题


YSS和恒生都无法解决的问题是3 过于复杂的业务、不成熟的技术决策产生的复杂度超过开发团队的掌控。

管理团队不懂微观技术（其实YSS高层也不懂，比如招我进去的总经理，他是清算第一代核心开发，非常了解业务，懂架构，也是他也搞不明白为啥团队技术上的问题在哪里），也没有解决思路，无法投入资源解决问题，只能盲试。

但是，他们宏观上的技术方案和嗅觉还是不错的，比如



- 直接完整的拥抱了微服务，没有half half，产生了不是1  +  1的复杂度，而是 2 * 2 的复杂度（因为每一种技术，都不但要考虑自己，还要考虑和对方的配合）
- 采用了微服务技术，但是并没有拆分的很微，而是很克制，保持了较粗的拆分粒度（微服务的IO容错、协作复杂度，会造成实现复杂度提升至少3倍左右，同样的业务，微服务实现天然要多3倍+的代码，团队资源）
- 关键业务组件都要求引擎化、组件化（导入，清算，交手，支付网关……）

可是新架构依然陷入困境。

为什么？

卡住YSS清算的核心并不是他们哪哪都有问题、顾此失彼，而是其中交收引擎本身过于复杂。团队没有人能设计和实现他。

他们架构（技术专家）的注意力大部分在技术上，比如用了分布式架构、监控、日志平台、缓存、异常码规范……等，也非常精通业务，但不知道如何将业务沉淀为领域架构设计。反而因为技术设计不合理，导致复杂度过高，导致交收引擎无法落地。

所谓交收引擎，其实是将业务明细拆分为清算明细，每笔明细对应一个收、付方，时间。他复杂在哪里？

- 业务上：每个客户，每种业务类型，费用类型，都可能有差异化；
- 技术上，海量数据：必须在分钟级完成，而微服务架构天然相比存储架构，就IO多，性能低，容易错；
- 非业务功能上：无论业务多么复杂，IO多少，一点都不能错。

是这三者交织的复杂。举个例子，因为架构上，复杂的业务要求交收服务有7、8层逻辑，分别处理交手日、账户、产品、机构、业务类型、费用类型……等等，而异常码又不是跨层传播透明————这意味着最外层的异常复杂度是里面7层的排列组合，并且每一层都要处理这样的复杂度。
更不用提IO性能，容错等等方面的复杂度叠加。

可是他们几任的架构师根本没有意识到系统稳定性不足、难以掌控是因为自己引入大厂异常码设计规范这个规范。没有意识到如何去剥离、降低IO容错和性能复杂度。

……

一旦能定位到问题，就解决了50%的问题。

 

# 根本困难

阿里中台运动失败后，行癫总结失败的原因说，阿里不缺技术，缺懂业务，懂设计的架构师。

究恒生，YSS新一代微服务系统陷入困境，他们缺业务么？不缺，有老恒生丰富的业务经验。他们缺技术么？也不缺，他们招聘了很多大厂技术能力很强的专家。

他们缺彼此的融合么？

阿里做中台的时候，很多做中台的人，本身在这个系统做了10多年，既懂这一块的业务，也有很强的技术造诣。

可是，为什么还是没有做成呢？

 
如今，Verb Coding已经能提到90%的开发工作量了，你输入一段话，他产出的是你过去几天甚至个把星期的工作量。可是我问Agent你能理解语言表层的含义，你能理解他底层的规律么？
Agent回答说不行，虽然O1/R1正阳的深度推理引擎有改善，可是Agent暂时依然无法替代人类对客观现象进行总结，归纳，逻辑演技，范式总结，范式泛化。

依然，没有银弹。
