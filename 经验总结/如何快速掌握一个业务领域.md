# 如何快速掌握一个业务领域

基本思想方法来自DDD

DDD的思想是系统的核心复杂度在业务，业务的核心复杂度在领域，领域的核心复杂度在聚合根

聚合根就比如一颗大树的根、大树无论如何枝叶繁茂，每个枝叶都必然和根中的某个毛细血管相连。

同理，DDD设计中认为，无论软件多么复杂，每个逻辑片段必然和聚合根中的某个数据项、或者值相关。

掌握了这一个点，就掌握了整个系统。

比如，经验丰富的支付系统专家，对着支付订单的订单对象，就大致能猜测出系统有那些模块，功能，什么流程。

# 事件风暴
 
    1，聚合根为起点
    2，以流程为依据
    3，梳理、头脑风暴流程中每个点可能的业务变化

**经过事件风暴过的设计，大概率在流程上是完整的、在功能上能覆盖未来短期一段事件内的变化。**

    另外，需要补充的是，聚合根的起点是人，终点是人，中间串联的流程是线。他们构成的结构命名为————交易结构。

这是架构上很重要的一个概念。并以此作为产品设计、分析、价值流分析的基本。

# ERP
    交易角色：客户，供应商
    
    交易结构：
            1. 订单=>库存=>销售回款=>账户
            2. 订单=>BOM=>采购单=>库存=>应付
            3. 订单=>生产单=>物料单=>库存单=>产品单=>库存

    产品上，其关键是订单，以订单为起点，以数字化为依托，进行整体资金、物料、生产的计划和衔接安排。实现最高的效率。
    在实操上，库存设计很关键。是抵御不确定性风险，在效率和风险之间平衡的关键。
    
    在技术架构上，平平无奇。除了资金财务部分是精髓外，其他模块基本都是简单的流程+CRUD。

# 风控 
    交易角色：交易相关方、风险对象、数据提供方 
    交易流程：事件/规则加载/数据访问计划和调度/规则引擎回调/警告结果聚合/事件回调

    其中当然有很多变化。
        1，如果是实时风控，第一步事件的实现有wait，最后有notify
        2，如果是事中、事后，第一步事件没有wait，最后是callback对应消费者的mq或者url
        3，如果是实时，规则加载是实时规则，否则是非实时规则
        4，如果是实时、第三步数据计划和调度是并发的。而非实时是串行的
        5，第五步，如果是简单规则，高度变化的，往往是EL。而如果是复杂的，变化不高的，可以是模型，脚本。后者如果要求高度运维，往往简化为EL+页面。
                当然，如果变化的规则是流程，涉及到多步骤，还有引入决策引擎。

以上是大多数风控系统的架构，以事件高效响应为设计原则。

如果是批量的，实时性要求不高，但数据量和计算量极大。往往采用以数据为中心的架构。

                比如传统架构的存储过程
                微服务架构下的内存计算引擎 
                恒生的投资监督，核心抽象是FRD————一个产品+日期的数据包————在此技术上进行规则计算、计算调度
                类似的更抽象的是Spark的RDD，一个内存的、流式的、分布式的可调度的数据包
 

# 清算

    交易角色：业务系统、内部账户、清算、外部账户
    交易流程：数据/清算/交收/支付/对账/凭证
    架构设计的关键：
        整体是pipeline架构，有错即整体回滚，确保完全资金正确。无丝毫差错。
        每个步骤都是引擎化，为了应对N多客户，产品，机构，账户……等造成的海量差异化配置。化变化为不变，满足核心业务可靠性，性能，一致性要求。

        清算引擎本质上是分离不同费用周期（费/息/罚 分别是 月/日/不固定周期）、不同处理流程的资金清算明细（交易/账户/事件）
        交收引擎的核心职责是分离不同业务明细为不同收付账户、时间。
            （举个最简单的例子，仅仅账户上的差异：除了海量不同账户类型做收付、有些用业务明细、有些用授信账户抵扣）
        支付是实际的收/付动作、需要解决不同渠道通讯协议、报文协议、加解密、业务协议等技术上的适配问题
        对账是对收/付动作的核对。
        凭证是会计业务，对实际的资金变化分科目、分录记录。

        技术组件上比较关键的是本地缓存、以及内存调度————比如交收大概有7类配置的排列组合，
        每种组合从数百到数万，总计大概有过万亿的内存对象量（即使每种组合精简到只有ID，在100亿左右内存就会卡死32G内存，频繁GC）
        所有组合还要在内存中按优先级进行路由筛选。内存本身是无论如何也承受比起这种级别的复杂度规模和计算量，只能进行分片调度。

        在工程上和设计上比较关键的是关注点分离。
        引擎即使开发完毕，但后续随着客户需求迭代。代码腐化速度极快，很快就会变得不可维护。
        工程上一定要和产品、研发团队明确分离方式、DSL契约规范。尽量将大部分业务变化消灭在配置化。技术上只对模型进行开发。
        否则这种高复杂度的业务规模迟早是hold不住的。

# Agent开发平台
    Agent开发平台的主要用户，不是开发，而是需求方。
    一方面是业务的瓶颈2/3在需求明确阶段，之前是铺人，之后是希望通过系统化的技术手段可控的推进。
    另一方面，Agent已经能胜任60%的开发工作，还需要人做一些前期设计把关、后期CodeRivw。
 
    智能体开发平台的核心作用，是需求标准化，产出符合架构规范的、良好的的提示词模板。

# 网关
    
    大部分的网关系统构造都和Netty的们输入/输出双流水线架构高度接近。
    这种架构具有极高的扩展性、灵活性。
    但都限于技术层，面临复杂的业务，大多数还是需要大量的技术组装工作。
    我唯一比较欣赏的是蚂蚁的超网系统（supergw），它几乎让任何通讯的技术复杂度归0. 这个系统被誉为蚂蚁一堆烂代码中的唯一的精品。
    
    蚂蚁supergw所在的金融交换部门的新一代架构是个层次架构。
    1，外层：组合调度系统，负责路由、分发、组合、批量组装、重试等。
    2，中层：4个职责系统，fininfo（信息），fininflux（流入），finbatch（批量），finoutflux（流出）
    3，内层：即是精髓所在supergw，一个系统负责和几千家不同通讯协议、加解密算法、报文协议……的外部机构对接。承担了海量的
    业务量，屏蔽了海量的技术差异，保证高可靠、高可配置、可扩展、可运维。
    
    而超网的架构设计，其实极为简单。
    1，在Netty的基础上扩展各种通讯协议、报文协议、加解密协议插件
    2，将这些扩展，在特定业务码的组织下，设计为配置表+Groovy脚本。参数的变化用配置解决，逻辑的变化用Groovy脚本配置表解决。
        例如某机构是http协议，url是 ：http://xxxxx/xxxx
        某结构是自动协议（比如机构名是ABC农行，则自定义一个通讯协议schema为ABC://xxxxxx/xxxxxx
        比如某机构通讯报文协议是8583，另一个是自定义，8583的直接配参数。自定义的参数为Groovy脚本名即可。
        ……
    3，内部，将这这复杂性屏蔽了，只暴露业务码+map业务参数。

    它是蚂蚁整个公司的技术防腐层，外部无论如何复杂、变化。它很轻易的屏蔽、化简了。

    我在蚂蚁见到过无数复杂业务，代码也写的极为复杂。supergw是唯一一个将极度复杂简化优雅到让人赞叹，挑不出毛病的。
    
# ETL

    ETL技术几十年的发展，最佳实践就是Spark。
    1，支持的数据源多
    2，性能好
    3，架构灵活，支持单机、也支持分布式
    4，逻辑灵活，流式语法表达能力强，简洁

    kettle等等，适合业务，不适合开发，可靠性和健壮性也存在较大问题。
